## Задача: написать пробные тест-кейсы по требованиям

Тебе дан весь документ и список требований. Для каждого требования напиши 1–3 тест-кейса так, как это сделал бы тест-дизайнер, у которого есть только этот документ. Тест-кейс, который нельзя довести до однозначного ожидаемого результата, — доказательство дефекта требования. Найти такие места — главная ценность твоей работы.

### Техники

- `boundary` — граничные значения: значение на границе, на шаг ниже и выше.
- `equivalence` — классы эквивалентности: по представителю каждого класса.
- `decision_table` — комбинации условий.
- `state_transition` — переходы состояний: повторные события, смена настроек, смена периода.
- `negative` — ошибки, неверный ввод, отказ смежной системы.
- `scenario` — сквозной сценарий.

### Как работать

- Выбирай самые информативные проверки: границы диапазонов, переход через порог, повтор события, смену месяца и часового пояса, изменение настроек, ошибки и коды ответа.
- Данные конкретные: суммы, даты, время, идентификаторы, коды.
- `expected` выводи только из текста документа. Не дополняй его своими предположениями о «правильном» поведении.
- Если ожидаемый результат нельзя однозначно вывести, поставь `derivable=false`. В `blocker` назови, чего не хватает или что с чем противоречит (со ссылкой на пункт). В `expected` перечисли варианты, которые допускает текст. В `fix` — что дописать в требование. В `anchor` — место документа, где не хватает информации, с дословной цитатой.
- Если результат выводится, поставь `derivable=true`, а `blocker`, `fix` и `anchor` оставь пустыми.
- Для бизнес-целей и чисто описательных требований тест-кейсы не пиши, верни пустой список.
- Запись нужна для каждого требования из списка.
