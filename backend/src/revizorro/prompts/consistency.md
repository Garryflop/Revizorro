## Задача: проверить набор требований на согласованность, понятность и совместную реализуемость

Тебе дан весь документ и реестр выделенных требований. Отдельные требования уже проверены. Ищи дефекты, которые видны только при сопоставлении нескольких мест документа.

### Свойства набора

$criteria

### Обязательные сверки

Пройди каждую пару и запиши все расхождения:

1. Цель ↔ функциональные требования ↔ нефункциональные: обеспечивают ли правила, источники данных и сроки то, что обещает цель (например, цель про «мгновенно», а правила работают с отложенными событиями).
2. Функциональные требования ↔ критерии приёмки: пересчитай каждый пример по правилам документа и сравни с ожидаемым результатом.
3. Функциональные требования ↔ требования к данным: хватает ли полей для правил, совпадают ли единицы.
4. Основная часть ↔ спецификация API: все ли нужные операции есть (чтение и запись), соответствует ли метод HTTP операции (GET не должен изменять данные), совпадают ли параметры, диапазоны, единицы и правила.
5. Внутри API: описание метода ↔ его содержимое; логика метода ↔ коды ответов ↔ тела ответов; заголовки и наличие тела запроса; типы одного поля в запросе, ответе и хранилище; перечень статусов ↔ описанные статусы; название раздела ↔ его содержимое.
6. Термины: одна сущность под разными названиями, одна величина в разных единицах.

### Что искать

- Прямые противоречия: требование против требования; требование против критерия приёмки, примера, схемы процесса, sequence-диаграммы; основная часть против дочерней спецификации API и наоборот.
- Скрытые противоречия, которые проявляются только на сценарии: последовательность событий, при которой два пункта предписывают разное поведение.
- Расхождения терминов и форматов: один объект назван по-разному; одна величина в разных единицах; одно поле разного типа в запросе, ответе и хранилище; несовпадающие коды и тела ответов; заголовок раздела противоречит его содержимому.
- Несовместимые ограничения (`set_feasible`): каждое требование выполнимо, а вместе — нет.
- Понятность набора (`set_comprehensible`): ключевые термины не определены, структура вводит в заблуждение, схемы обрывочны.

### Контрпример обязателен для каждого противоречия

`counterexample`: конкретные исходные данные (суммы, даты, время, состояние), шаги и для каждой стороны — что предписывает её пункт (`basis` = «по Ф-3», `result` = …). Перепроверь арифметику и логику: контрпример должен однозначно показывать конфликт. Если честный контрпример построить не удаётся, это не противоречие.

### Локации

Укажи все места, участвующие в дефекте, — минимум две локации для противоречия, — и `rids` всех связанных требований.
